# Инструкции для работы с проектом

## О проекте

- Разрабатываем Android-приложение для изучения кандзи.
- Основной язык разработки — Kotlin.
- При разработке следовать актуальным стандартам и рекомендуемым практикам Android и Kotlin.

## Обязательная многоязычность

- Приложение многоязычное и ориентировано прежде всего на русскоязычную аудиторию. Русский — основной язык и язык подстановки при отсутствии перевода.
- Это обязательное правило без исключений: все решения о таблицах БД, моделях данных, коде, интерфейсе, учебном контенте, импорте, экспорте и проверках должны учитывать многоязычность и приоритет русскоязычной аудитории.
- Переводимые данные отделять от независимых от языка сущностей; добавление языка не должно требовать новых столбцов для каждого языка или изменения бизнес-логики. Язык переводов обозначать полем `language_tag`.
- Таблицы переводов именовать единообразно: полное имя основной таблицы + `_translations`, например `radicals_translations` и `kanji_translations`.
- Пользовательские тексты выносить в ресурсы локализации или хранилище переводов; идентификаторы и бизнес-логика не должны зависеть от переведённых строк.
- Подробные требования: [doc/implementation/localization.md](doc/implementation/localization.md). Нарушать это правило нельзя.

## Архитектура и навыки

- Перед изменением кода читать `doc/architecture.md` и следовать принятым требованиям: Compose, Clean Architecture, модульность и атомарные UI-компоненты.
- Использовать стабильные библиотеки и API. Каждое новое применение experimental/preview API и соответствующего opt-in требует предварительного явного разрешения пользователя на конкретный API и область использования. Общее поручение реализовать функцию не является таким разрешением. Согласованные исключения фиксировать в `doc/decisions/experimental-api.md`; разрешение не распространяется автоматически на другие API или модули. Не вводить экспериментальные флаги языка и legacy-подходы.
- Перед выбором или применением библиотеки/API проверять её возможности, актуальное состояние и рекомендуемый способ использования через Context7 по официальной документации. Сверять результат с фактически подключёнными версиями и совместимостью проекта; не считать пример для последней версии доступным в текущей. Проверка не является согласованием изменения проекта. Обновление зависимостей и применение experimental/preview API с opt-in допускаются по предварительному явному согласованию с пользователем; без согласования не вводить их. Для experimental API согласование должно указывать конкретный API и область использования, как описано выше. Если Context7 недоступен или сведений недостаточно, явно отмечать ограничение и проверять официальные источники/исходники соответствующей версии. Существенные выводы и технический выбор сохранять в `doc/` со ссылками и версиями.
- Для любой задачи в первую очередь искать решение штатными возможностями используемой платформы и стандартными API — это общее правило, не только для UI или переноса карточек. Сначала проверять существующий механизм, его возможности и ограничения; не начинать с собственной реализации. Для Android максимально использовать Android/Compose, для остальных задач — средства соответствующей платформы. Собственную логику или стороннюю библиотеку вводить только для действительно отсутствующего поведения, с обоснованием и документированием границы в `doc/`; не заменять готовые платформенные механизмы самодельными аналогами.
- DI через конструкторы обязателен; начальный вариант — ручная сборка графа. Hilt не обязателен; выбор DI-фреймворка документируется отдельно.
- Локальные навыки находятся в `.agents/skills/`. Состав и маршрутизация описаны в `doc/development-skills.md`. Для соответствующей задачи читать нужный `SKILL.md`; не загружать все навыки без необходимости.
- Навыки помогают выполнять требования проекта, но не заменяют их. Не переносить версии и шаблоны из внешних примеров без проверки совместимости.

## Документация

- Каноническая терминология обязательна во всех слоях: [глоссарий](doc/glossary.md). `Recipe` / «рецепт» — сохранённая конфигурация; `Training` / «тренировка» — выполнение по рецепту. Не называть рецепт тренировкой, а выполнение — продуктовой «сессией». Схема БД, домен, интерфейс и HTML используют одинаковые бизнес-имена; технические API вроде `sessionStorage` не являются бизнес-сущностями.

- Радиус всех текстовых полей, включая поиск, числовые/многострочные поля и диалоги, задаётся только `component_shape.text_field` в `doc/design-system/theme/theme-source.json`. После изменения запускать `npm run build --prefix doc/design-system/theme`: команда обновляет общий CSS и Android dimension. В Compose использовать `MaterialTheme.inputShape` из `core:designsystem`, не локальные радиусы; генерируемый `input-shape.xml` вручную не править. Проверять `python3 doc/verification/check-input-shapes.py`. Радиусы карточек, кнопок и нетекстовых контролов независимы.

- Каноническая карта экранов и виджетов — `doc/project-map.md`. Перед изменением интерфейса находить затрагиваемые ID и проверять повторные применения общих компонентов. При добавлении, удалении, переносе или изменении экрана/виджета обновлять карту в том же изменении: иерархию, краткое описание, источник реализации и область влияния. Присвоенные ID постоянны: не перенумеровывать при перестановке, не переиспользовать удалённые ID; удалённые оставлять в разделе выведенных ID. В обсуждении правок использовать эти ID. Различать общий компонент, его экземпляр и похожие, но независимые реализации; указывать транзитивное влияние общих компонентов. Использовать единые иерархические ID фич в карте и HTML-реестре (`HOME`, `BOOKS`, `REFS`, `DICT`, `TRAIN`, `SHARED`, `SELECT`, `PRACTICE`, `SETTINGS` и их потомки). Перенумерация допустима только по прямому запросу пользователя с таблицей соответствий и совместимостью старых ссылок; согласованная миграция 2026-11-05 описана в `doc/screen-id-migration.md`, прежние ID зарезервированы. Обновлять одновременно карту, `doc/design-system/theme/screens.json`, HTML-просмотрщик и затронутые актуальные ссылки/тесты; исторические отчёты и снимки не переписывать. Карта должна отражать текущую реализацию и явно отмечать прототипы/непроверенные состояния, а не выдавать согласование HTML за готовый Android.

- Учебный словарь допускает отдельные слова, выражения и полные предложения, когда это необходимо для обучения. Не ограничивать модель одним словом и не удалять законченные фразы или значимые формы употребления механически при очистке данных. См. `doc/database/words.md`.

- Вся документация, спецификации, скриншоты и технические решения хранятся в директории `doc/`.
- `README.md` описывает актуальный итог: назначение, действующие требования, устройство, поведение, ограничения и ссылки на спецификации. Не включать в README историю обсуждений, ход сессий, промежуточные варианты, последовательность правок и формулировки «после замечания», «сначала сделали», «потом согласовали». При изменениях переписывать затронутый раздел целиком до актуального состояния, а не дописывать отменяющие друг друга уточнения. Текущий статус реализации и границы проверки указывать явно, без выдачи макета за готовую реализацию. Историю хранить в Git; необходимые отчёты проверок и обоснования решений — в отдельных документах `doc/`.
- Перед реализацией изменений изучать относящиеся к задаче материалы в `doc/`.
- Новую документацию и принятые технические решения также сохранять в `doc/`.
