# Инструкции для работы с проектом

## О проекте

- Разрабатываем Android-приложение для изучения кандзи.
- Основной язык разработки — Kotlin.
- При разработке следовать актуальным стандартам и рекомендуемым практикам Android и Kotlin.

## Обязательная многоязычность

- Приложение многоязычное и ориентировано прежде всего на русскоязычную аудиторию. Русский — основной язык и язык подстановки при отсутствии перевода.
- Это обязательное правило без исключений: все решения о таблицах БД, моделях данных, коде, интерфейсе, учебном контенте, импорте, экспорте и проверках должны учитывать многоязычность и приоритет русскоязычной аудитории.
- Переводимые данные отделять от независимых от языка сущностей; добавление языка не должно требовать новых столбцов для каждого языка или изменения бизнес-логики. Язык переводов обозначать полем `language_tag`.
- Таблицы переводов именовать единообразно: полное имя основной таблицы + `_translations`, например `radicals_translations` и `kanji_translations`.
- Пользовательские тексты выносить в ресурсы локализации или хранилище переводов; идентификаторы и бизнес-логика не должны зависеть от переведённых строк.
- Подробные требования: [doc/implementation/localization.md](doc/implementation/localization.md). Нарушать это правило нельзя.

## Архитектура и навыки

- Перед изменением кода читать `doc/architecture.md` и следовать принятым требованиям: Compose, Clean Architecture, модульность и атомарные UI-компоненты.
- Использовать стабильные библиотеки и API. Каждое новое применение experimental/preview API и соответствующего opt-in требует предварительного явного разрешения пользователя на конкретный API и область использования. Общее поручение реализовать функцию не является таким разрешением. Согласованные исключения фиксировать в `doc/decisions/experimental-api.md`; разрешение не распространяется автоматически на другие API или модули. Не вводить экспериментальные флаги языка и legacy-подходы.
- DI через конструкторы обязателен; начальный вариант — ручная сборка графа. Hilt не обязателен; выбор DI-фреймворка документируется отдельно.
- Локальные навыки находятся в `.agents/skills/`. Состав и маршрутизация описаны в `doc/development-skills.md`. Для соответствующей задачи читать нужный `SKILL.md`; не загружать все навыки без необходимости.
- Навыки помогают выполнять требования проекта, но не заменяют их. Не переносить версии и шаблоны из внешних примеров без проверки совместимости.

## Документация

- Учебный словарь допускает отдельные слова, выражения и полные предложения, когда это необходимо для обучения. Не ограничивать модель одним словом и не удалять законченные фразы или значимые формы употребления механически при очистке данных. См. `doc/database/words.md`.

- Вся документация, спецификации, скриншоты и технические решения хранятся в директории `doc/`.
- `README.md` описывает актуальный итог: назначение, действующие требования, устройство, поведение, ограничения и ссылки на спецификации. Не включать в README историю обсуждений, ход сессий, промежуточные варианты, последовательность правок и формулировки «после замечания», «сначала сделали», «потом согласовали». При изменениях переписывать затронутый раздел целиком до актуального состояния, а не дописывать отменяющие друг друга уточнения. Текущий статус реализации и границы проверки указывать явно, без выдачи макета за готовую реализацию. Историю хранить в Git; необходимые отчёты проверок и обоснования решений — в отдельных документах `doc/`.
- Перед реализацией изменений изучать относящиеся к задаче материалы в `doc/`.
- Новую документацию и принятые технические решения также сохранять в `doc/`.
