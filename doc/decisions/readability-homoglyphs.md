# Обработка омоглифов кандзи и катаканы в проверке читаемости

Статус: **действующее решение** (Вариант 2 — Top-3 кандидата) с целевым развитием до **Варианта 3** (комбинированный подход с таблицей эквивалентов).

## 1. Проблема

В японской письменности знаки катаканы исторически формировались из элементов кандзи. В результате ряд знаков катаканы и кандзи в изолированном рукописном написании являются **полными визуальными близнецами (омоглифами Unicode)**:

| Кандзи | Unicode | Катакана / знак | Unicode | Значение кандзи | Чтение катаканы |
|---|---|---|---|---|---|
| **二** | `U+4E8C` | **ニ** | `U+30CA` | два | ни |
| **口** | `U+53E3` | **ロ** | `U+30ED` | рот | ро |
| **一** | `U+4E00` | **ー** | `U+30FC` | один | знак долготы (тёомпу) |
| **力** | `U+529B` | **カ** | `U+30AB` | сила | ка |
| **夕** | `U+5915` | **タ** | `U+30BF` | вечер | та |
| **八** | `U+516B` | **ハ** | `U+30CF` | восемь | ха |
| **工** | `U+5DE5` | **エ** | `U+30A8` | ремесло | э |
| **ト** | `U+535C` | **ト** | `U+30C8` | гадание (радикал) | то |
| **匕** | `U+5315` | **ヒ** | `U+30D2` | ложка (радикал) | хи |
| **又** | `U+53C8` | **ヌ** | `U+30CC` | снова | ну |
| **九** | `U+4E5D` | **ク** | `U+30AF` | девять | ку |

### Поведение ML Kit Digital Ink Recognition
- Модель распознавания рукописного ввода обучалась на смешанном японском корпусе текстов.
- При вводе знака в отдельной клетке контекст отсутствует (`preContext == ""`), и целевой знак модели не сообщается (согласно принципу чистоты проверки).
- Для изолированных рукописных начертаний вроде двух горизонтальных линий (`二` / `ニ`) или квадрата (`口` / `ロ`) модель статистически почти всегда ставит катакану на **1-е место** (`candidates[0]`), а правильный кандзи — на **2-е или 3-е место**.
- При проверке только первого кандидата (`candidates.firstOrNull() == expected`) кандзи `二`, `口`, `一` систематически отклонялись чекером читаемости (`CheckVerdict.Incorrect`), хотя ученик написал знак абсолютно верно.

## 2. Действующая реализация: Вариант 2 (Top-3 кандидата)

В чекер читаемости [`DigitalInkKanjiChecker.kt`](../../checker/readability/src/main/kotlin/ru/mobui/kanji/checker/readability/DigitalInkKanjiChecker.kt) внедрена проверка наличия целевого кандзи среди первых 3 кандидатов модели (`MAX_READABILITY_CANDIDATES = 3`):

```kotlin
internal fun evaluateCandidates(
    candidates: List<String>,
    expected: String,
    maxCandidates: Int = MAX_READABILITY_CANDIDATES,
): Pair<CheckVerdict, String> {
    val top = candidates.take(maxCandidates).map { it.trim() }
    val matched = top.contains(expected)
    val recognized = if (matched) expected else top.firstOrNull().orEmpty()
    val verdict = if (matched) CheckVerdict.Correct else CheckVerdict.Incorrect
    return verdict to recognized
}
```

### Свойства решения:
1. Если на 1-м месте катакана `ニ`, а на 2-м месте кандзи `二`, знак признаётся верным (`CheckVerdict.Correct`).
2. В `recognizedText` для интерфейса записывается `expected` (при совпадении) или первый кандидат (при несовпадении).
3. В диагностические метрики отчёта (`metrics["candidates"]`) сохраняется срез кандидатов для отладки.
4. Безопасность: независимый контроль геометрии, пропорций и крючков остаётся за чекером формы (`:checker:shape`), а контроль направления штрихов — за чекером порядка (`:checker:writing`). Даже если посторонний символ попадет на 3-е место в ML Kit, чекер формы не допустит принятия ошибочного знака.

## 3. Целевое проектирование: Вариант 3 (Комбинированный подход с таблицей омоглифов)

Для последующего развития и предельно строгой валидации спроектирован комбинированный подход:

### Архитектура Варианта 3:
1. **Таблица канонических омоглифов**:
   Формируется закрытый справочник пар визуальных эквивалентов:
   ```kotlin
   private val HOMOGLYPHS: Map<String, Set<String>> = mapOf(
       "二" to setOf("ニ"),
       "口" to setOf("ロ"),
       "一" to setOf("ー", "―", "‐"),
       "力" to setOf("カ"),
       "夕" to setOf("タ"),
       "八" to setOf("ハ"),
       "工" to setOf("エ"),
       "ト" to setOf("卜"),
       "匕" to setOf("ヒ"),
       "又" to setOf("ヌ"),
       "九" to setOf("ク"),
   )
   ```
2. **Двухуровневое правило принятия**:
   - **Уровень 1 (Прямой или омоглифный 1-й кандидат)**: Если `topCandidate == expected` ИЛИ `topCandidate in HOMOGLYPHS[expected]` → `CheckVerdict.Correct`. В этом случае мы уверены, что модель на 1-м месте увидела именно ту графическую форму, которую ожидали.
   - **Уровень 2 (Fallback на Top-K при омоглифии)**: Если 1-й кандидат не совпал, но входит в семантически близкие начертания, а `expected` присутствует во 2-й или 3-й позиции с высоким баллом уверенности (`score`), ответ также принимается.
   - Для знаков, **не** имеющих омоглифов (например, `曜`, `鬱`, `森`), требование к 1-му кандидату может оставаться более строгим.

3. **Связь с остальными чекерами**:
   Консенсус трёх чекеров (`CombinedKanjiChecker`) гарантирует, что даже полное визуальное совпадение формы катаканы не пройдёт проверку, если не соблюдены правила написания кандзи (например, разница длин верхней и нижней черты в кандзи `二`, где нижняя черта длиннее верхней, что контролируется словарным правилом `ShorterThan` в `:checker:shape`).
