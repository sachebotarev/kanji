# Конструктор рецептов: целевая модель хранения

Статус: доменные модели, Room entities/DAO, транзакционный репозиторий рецептов и Compose-конструктор подключены. [Согласованная спецификация](../design-system/05-screens/recipe-builder.md), [контракт реализации](../implementation/approved-ui-handoff.md). SQL ниже описывает ограничения; актуальный экспорт Room — [1.json](../../data/catalogdb/schemas/ru.mobui.kanji.data.catalog.CatalogDatabase/1.json). Все последующие изменения схемы выполняются миграциями с сохранением пользовательских данных.

`task_count` и `seconds_per_symbol` — сохранённые параметры рецепта, не исполнение. Выполнение хранится в [trainings.md](trainings.md) (Room 1, `TrainingsRepository`).

## Схема и порядок установки

1. Существующие таблицы каталога/личных слов Room 1.
2. [Теги личного словаря](personal-dictionary.sql).
3. [Рецепты и материалы](recipes.sql).

`recipes` хранит стабильный UUID, позицию, активный выбор, параметры, ревизию и архивный признак. `recipes_translations` хранит названия по `language_tag`; нет отдельных колонок ru/en. Выбранный рецепт не может быть архивной; активных не больше одной. При пустом списке активной нет. Порядок чтения — `position, id`, без требования уникальных позиций на уровне SQL, чтобы перестановка выполнялась в одной транзакции без промежуточного конфликта.

`task_count` — положительное число или NULL (по числу уникальных записей); `seconds_per_symbol` — положительные секунды на practice-символ или NULL (без таймера); лимит слова = секунды × число символов для письма (UI по умолчанию при включении таймера — 10). Режим рецепта только `shuffled_cycles`. Какие знаки требуют ввода при главах учебника — [training-input-rules.md](../implementation/training-input-rules.md).

## Материалы

`recipe_materials` содержит UUID материала, UUID рецепта, порядок и `material_type`:

| Тип | `source_id` | Сохраняемые условия |
|---|---|---|
| `book` | Реальный ID источника типа textbook/book | `recipe_materials_chapters`, `recipe_materials_kanji` |
| `dictionary` | Реальный ID единственного личного источника | `recipe_materials_tags`, `recipe_materials_kanji` |
| `kanji` | NULL | `recipe_materials_jlpt`, `recipe_materials_kanji` по всей базе |
| `words` | NULL | `recipe_materials_words` — точный набор ID |

`material_id` в дочерних `recipe_materials_*` — UUID **материала**, не ID учебника. Главы строго положительны, как `source_kanji.chapter_number` действующей базы. Составной PK каждой связи запрещает повторы; FK запрещают потерянные ссылки. Выбранная глава должна существовать в выбранном учебнике.

У материала типа `kanji` уровни JLPT сохраняются в `recipe_materials_jlpt` (точные `1…5` и/или `-1` «нет данных»): это условие набора, не одиночный `jlpt_level` на весь рецепт. Ключи, число черт и поиск в селекторах остаются временными фасетами и в материал не пишутся; явные кандзи — в `recipe_materials_kanji`. Режим кандзи только ANY/ИЛИ; неподдерживаемый переключатель ANY/ALL не переносится из старого проекта модели.

## Предикаты набора

- Внутри выбранных глав — ИЛИ; внутри кандзи — ИЛИ; внутри JLPT — ИЛИ; внутри тегов — ИЛИ.
- Разные группы условий одного материала — И.
- Материалы объединяются по ИЛИ, дедупликация по `words.id`, порядок входов детерминированный.
- Пустые теги/главы/кандзи/JLPT означают отсутствие соответствующего ограничения; пустой `words` — пустой набор, не вся база.
- Личный материал всегда ограничен активными пользовательскими записями и личным источником. Каталожные записи не получают пользовательские теги.
- При фильтрации учебника учитывать его реальные `source_words` и `source_kanji`, не глобальное совпадение знака: связь с главой получается через размещение кандзи этого же учебника. Личные записи не попадают в учебный материал.
- Архивные слова и источники исключаются из вычисления. Удалённые/архивные явные слова не заменяются случайными; материал может стать пустым. Ошибка пустого материала показывается при сохранении/редактировании, не подменяет набор.

## Транзакции и валидация репозитория

Сохранение рецепта проверяет непустое локализованное название (1–120 символов), BCP 47, уникальные канонические языки, хотя бы один материал и непустой результат каждого материала; затем атомарно записывает рецепт, переводы и дочерние связи. Новая ревизия проверяется оптимистично. Отмена черновика не пишет в БД. Смена типа материала очищает не относящиеся к нему связи внутри той же транзакции. Проверять итоговый агрегат после изменения родительского источника: типы дочерних связей, принадлежность глав/кандзи учебнику и актуальность явных слов. SQL не заменяет проверку непустоты агрегата и всех контекстных ограничений.

Радиокнопка меняет активный рецепт атомарно: снять прежний выбор, установить новый. При архивировании/удалении активного рецепт больше не выбран; другой рецепт автоматически не выбирается. Сортировка обновляет позиции в транзакции, не меняет активный ID. Доступные команды перемещения и жест вызывают один сценарий; при непустом поиске перемещение отключено.

Удаление тега физически удаляет его переводы, `word_tags` и `recipe_materials_tags` каскадно, но не слова/рецепты. Удаление последнего условия снимает ограничение по тегам, как в согласованном HTML. Репозиторий инвалидирует наблюдаемые наборы слов и рецептов. Архивирование слова исключает его из выдачи, сохраняя идентичность и возможность восстановления.

## Локализация и границы

Названия разрешаются: текущий канонический язык → базовый язык → русский → детерминированное существующее название. Создание перевода на текущем языке не копирует fallback автоматически в новый перевод. Бизнес-правила и сравнения используют ID, не названия.

Полный текст слова/выражения/предложения сохраняется. Лимит имени рецепта не распространяется на написание или чтение слова.

DDL рецептов не создаёт таблицы выполнения. Контракт и Room-реализация тренировок — [trainings.md](trainings.md) / [trainings.sql](trainings.sql).
